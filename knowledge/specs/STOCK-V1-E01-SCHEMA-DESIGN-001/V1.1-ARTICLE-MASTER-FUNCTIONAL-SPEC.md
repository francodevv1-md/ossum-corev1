# V1.1 — Article Master Functional Specification

Status: Functional Definition Validated — implementation remains out of scope

## Goal

Make the article master the canonical catalog used by stock, receipts, scanning, supplier documents, surgical preparation, boxes, remitos, consumption, and returns.

Creating an article creates catalog identity only. It does not create physical stock.

## Functional scope

### 1. General data

- Automatic OSSUM code (`ITM-...`).
- Description.
- Operational article type: `STANDARD` or `COMPOSITE`.
- Product classification: Category → Subcategory → optional third level. Implant, instrument, disposable, equipment, and similar labels belong to this product axis, not to the operational type.
- Independent Brand, Manufacturer, and optional Product Line.
- Independent Clinical Family, model, and measure or variant.
- Unit of measure.
- Optional operational metadata already supported by Stock where it does not duplicate the canonical identity.

`COMPOSITE` is derived only when `CajasBoxFormula.currentVersionId` is present. `CajasBoxFormula` identifies a box model and `StockIdentifiedUnit` identifies a physical box; neither is inferred from operational type alone. Legacy Fabricado/Reventa remains preserved evidence until its semantics are defined and is not mapped automatically.

Only identity-critical fields are required for initial save. Missing operational information produces a visible pending-data indicator, not an artificial block.

### 2. Product identifiers

An article may have many identifiers. Each identifier stores its type and normalized value, with optional manufacturer and supplier context.

Supported types:

- Manufacturer reference.
- GTIN / EAN.
- Supplier code.
- Alternative code.
- OSSUM code.

Identifier resolution depends on identifier type and context:

| Identifier | Resolution rule |
| --- | --- |
| GTIN / EAN | Must resolve uniquely after normalization. |
| Manufacturer reference | May require manufacturer context to resolve uniquely. |
| Supplier code | Must be evaluated with the supplier context. |
| OSSUM code | Must resolve uniquely. |
| Alternative code | Resolves only when its configured scope is unambiguous. |

If the available context does not produce one unambiguous article, OSSUM must surface the candidates and ask the user to resolve them. It must never assign an ambiguous identifier silently or overwrite an existing mapping without explicit confirmation.

The form supports:

- Add identifier manually.
- Scan identifier.
- Show existing identifiers.
- Deactivate an obsolete identifier without deleting historical evidence.

### 3. Traceability policy

The article defines the policy for future physical stock:

- None.
- Lot.
- Lot + expiry.
- Serial.
- Serial + expiry.
- Lot + serial + expiry.

The policy belongs to the article configuration. Lot, serial, and expiry values belong to received stock evidence and must never be stored as permanent article attributes.

Changing the policy is prospective and cannot invalidate existing stock or pending reservations.

UDI / GS1 is not a traceability-policy option. It is an input format interpreted by Scan Core. A GS1/UDI scan may carry an article identifier plus lot, serial, and expiry evidence; the article policy determines which of those physical values are required for stock operations.

### 4. Supplier mappings

Store supplier-specific code mappings:

`Supplier + supplier code → Article`

Mappings are reusable by manual receipt, invoice OCR, delivery-note OCR, and reconciliation. A low-confidence or conflicting match remains pending for user review.

### 5. UX/UI continuity

Any modification or extension of the article form must continue the existing Stock / Artículos experience:

- Reuse the current layout, section hierarchy, spacing, controls, labels, dialogs, tables, and interaction patterns.
- Extend the existing visual language instead of redesigning the Stock module.
- Keep the current dense operational presentation and responsive behavior.
- Do not introduce a separate visual system, navigation model, or interaction language for identifiers, scanning, or traceability.

The new fields and actions must feel like a natural extension of the current Stock / Artículos screens.

## Scan behavior

The article form may invoke the shared Scan Core. Scan Core returns normalized evidence, including:

- Raw scanned value.
- Detected symbology when available.
- GTIN/reference/other identifier candidates.
- Lot, serial, and expiry candidates when encoded.

During article creation, product identity candidates may prefill identifiers. Physical traceability candidates are preview-only until a receipt assigns them to stock.

## Acceptance criteria

1. A user can create an article with the minimum identity fields and receive an automatic OSSUM code.
2. A user can add multiple manufacturer, GTIN/EAN, supplier, and alternative identifiers.
3. A scanned known identifier resolves to the existing article instead of creating a duplicate, using the identifier's required context.
4. GTIN/EAN resolves uniquely; manufacturer references and supplier codes use their manufacturer/supplier context when required.
5. A scanned unknown identifier can remain pending or be linked explicitly to an article.
6. A supplier code mapping can be created and reused by later document matching.
7. A traceability policy can be selected without creating a lot, serial, or expiry record.
8. UDI/GS1 is interpreted by Scan Core and does not become an article traceability-policy value.
9. After save, the article is immediately available for search and selection in Stock, Recepción, and Preparación, initially with stock `0` until a real stock movement exists.
10. Saving an article does not alter stock balances or create a stock movement.
11. Historical identifier evidence is preserved when an identifier is deactivated.
12. Ambiguous identifiers are surfaced for resolution and never auto-assigned silently.
13. Any form extension preserves the existing Stock / Artículos UX/UI structure and interaction language.

## Out of scope

- Prisma schema or migration design.
- Stock receipt creation or stock movement.
- StockTraceUnit creation.
- Preparation, reservation, box content, remito, consumption, or returns.
- OCR execution and automatic stock entry.
- Camera scanner application.
- Production data migration or backfill.

## Dependencies

- Existing Stock article UX and current mock fields.
- Approved Stock V1 hybrid traceability rules.
- Shared Scan Core definition.
- Company-scoped identity and authorization rules before implementation.

## Functional definition validation

This definition incorporates the required separation between Scan Core formats and article traceability policy, contextual identifier resolution, immediate cross-module article availability with stock `0`, and Stock / Artículos UX/UI continuity. No schema, migration, API, or UI implementation is authorized by this document.
