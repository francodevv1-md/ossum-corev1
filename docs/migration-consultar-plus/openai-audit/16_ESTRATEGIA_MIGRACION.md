# Arquitectura propuesta (no implementada)

Extracción read-only → staging JSON/Parquet fuera del backup, versionado con checksum/encoding y valores originales → validación con severidad → resolución de identidad/dependencias → historical writer transaccional aislado → reconciliación → rollback compensatorio. Descartar reutilizar services normales a ciegas (numeración/notificación/stock); evitar `importMode` global que contamine lógica normal. DB staging podría agregarse después, solo si retención/volumen/transacciones lo justifican.

Ledger conceptual: MigrationRun (fuente/snapshotHash/predicado/versión/estado), LegacyEntityRef (`companyId,source,entityType,legacyId, targetEntityId, createdByRunId, lastSeenRunId, inputHash, ownership`), MigrationError y MigrationReconciliationReport; más tabla de intentos/efectos inmutables por run. UNIQUE **(companyId,source,entityType,legacyId)**, no incluir migrationRunId ni inputHash en la unicidad de identidad. Para objetos de detalle cuya clave solo es local al padre, `legacyId` compuesto estable y tipado. Cambio de hash obliga diff/revisión, no duplicado. CREATED solo eliminable cuando ningún vínculo nativo/posterior existe; REUSED nunca borrar; UPDATED requiere before-image y revisión de cambios posteriores; SKIPPED/REJECTED sin eliminación. Resolver `companyId` antes del ledger; `organizationId` también importa para Article. Reconciliar sumas origen/elegibles/rechazados/creados/reutilizados/actualizados/skipped/error y comparar campos representativos por entidad, no solo totales. Stock: snapshot inicial conciliado + movimientos posteriores, histórico previo sin afectar saldos; fecha corte y consistencia de saldos pendientes.
