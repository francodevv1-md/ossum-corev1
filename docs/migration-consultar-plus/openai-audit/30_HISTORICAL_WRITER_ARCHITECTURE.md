# Historical Surgery writer — decision and actual side effects

**Choose D: read-only staging → validator → tenant-aware historical writer**, using reusable *pure* validators and reference checks, not the normal creation path. Do not implement yet. `createSurgery` rejects historical initial cxStatus other than `pending` (`surgery.validator.ts:278–303`), allocates visibleNumber and creates AuditEvent (`surgery.service.ts:732–797`); calling it once then changing status would invent a transition and potentially notifications. `importMode` on this routine would split its invariants and risk live behavior. Direct unvalidated Prisma is forbidden: writer must check company, company-scoped ContactCompanyLink, duplicate ledger key, patient required, optional roles, date/status mapping, snapshot hashes; it must create target + ref + RunItem + migration AuditEvent in one transaction with retryable uniqueness handling. Keep operation unexposed to public APIs and separately reviewed for permissions.

Verified **create** of Contact/Article/Surgery itself does NOT write Invoice, Remito, Consumo or StockMovement in the cited service paths. Notifications occur on Surgery status mutation (`surgery.service.ts:908–1000`), **not** on create: never fake a status transition to reach FIN. Service `linkContactToCompany` upserts and overwrites roles (`contact.service.ts:524–543`); do not call to “add another role” to a reused native Contact. AuditEvent requires a valid user (`schema.prisma:1337–1360`); selecting an actor or changing permissions is a separate approval gate. Existing productive service files are left untouched.
